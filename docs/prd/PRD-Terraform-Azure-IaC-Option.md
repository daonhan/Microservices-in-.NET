## Problem Statement

The repo provisions all Azure infrastructure with Bicep — 15 files orchestrated by `main.bicep`, applied manually via `az deployment group create`, owning the dev, staging, prod, and (cost-optimized) sandbox environments. As a developer who wants Terraform experience and a second, independently-owned Azure provisioning lane, there is today no way to stand up the full microservices stack on Azure with Terraform. Adding Terraform naively risks two IaC tools mutating the same resources (drift and ownership wars), so the effort needs a clear ownership boundary, its own state backend, its own CI/CD lane, and a recorded decision — none of which exist.

## Solution

Introduce Terraform as a **second, parallel** Azure IaC lane that owns a brand-new, self-contained environment, `sbx2` (`10.50.0.0/16`, southeastasia, its own resource group), while Bicep keeps dev/staging/prod **and its existing `sandbox` env untouched**. No resource is ever owned by both tools, so there is nothing to `terraform import`.

Terraform provisions the full data plane for `sbx2` (VNet + AKS + ACR + SQL with 7 databases + Redis + Service Bus with 11 topics + Key Vault), mirroring the existing cost-minimizing sandbox SKU profile so the learning environment stays cheap. State lives in an `azurerm` Storage Account backend (blob-lease locking, one state key per env), bootstrapped once by a committed script. A new Azure Pipeline (`terraform-pipeline.yml`) authenticates via a dedicated Workload Identity Federation service connection and runs a `validate → plan-artifact → approved-apply` flow gated by a `tf-sbx2` Azure DevOps Environment. A GitHub Actions workflow runs `fmt`/`validate`/`tflint` as a credential-free PR gate, mirroring the existing kubeconform manifest gate. The microservices then deploy onto `sbx2` through the existing shared `deploy-stage.yml` template (extended with a `sbx2` target + `SBX2_` variable group), self-migrating their schema at startup via `Qa__Seed=true`. ADR 0015 records the dual-tool decision.

## User Stories

1. As a developer, I want Terraform to provision a complete Azure environment, so that I gain Terraform experience without touching the Bicep-managed environments.
2. As a developer, I want Terraform to own a brand-new env `sbx2` separate from Bicep's existing `sandbox`, so that no resource is ever mutated by two tools.
3. As a developer, I want `sbx2` to use a non-overlapping `10.50.0.0/16` VNet in southeastasia, so that it could be peered later without CIDR collisions with the existing `10.40` sandbox.
4. As a developer, I want Bicep's dev/staging/prod/sandbox definitions left completely unchanged, so that there is zero regression risk to existing environments.
5. As a developer, I want no `terraform import` of live resources, so that the greenfield env avoids the high-risk adoption of the 7-DB SQL server, `listKeys`-backed secrets, and seeded role assignments.
6. As a developer, I want Terraform to provision the VNet with three subnets (AKS `/20`, private-endpoints `/24`, agents `/24`), so that the network shape matches the established Bicep topology.
7. As a developer, I want Terraform to provision an ACR owned by `sbx2`, so that the environment is self-contained and does not depend on a shared registry it does not own.
8. As a developer, I want Terraform to grant the AKS kubelet identity the `AcrPull` role on the ACR via `azurerm_role_assignment`, so that pods pull images without a deterministic `guid()` seed (the Terraform resource address is already stable).
9. As a developer, I want Terraform to provision AKS with a system-assigned managed identity and Container Insights wired to a Log Analytics workspace, so that the cluster matches the Bicep observability posture.
10. As a developer, I want Terraform to provision one Azure SQL logical server with 7 databases (auth/order/product/inventory/shipping/payment/saga) declared via a `for_each` map, so that database creation stays DRY.
11. As a developer, I want the SQL admin password generated by `random_password` and held only in state, so that no secret is hardcoded in the configuration.
12. As a developer, I want Terraform to provision Redis and a Service Bus namespace with 11 topics (declared via `for_each`) matching the integration-event set, so that messaging works end-to-end on `sbx2`.
13. As a developer, I want Terraform to provision an RBAC-enabled Key Vault that stays provisioned-but-unwired from pods (parity with today), so that I do not expand scope into Key Vault CSI in this iteration.

16. As a developer, I want one state key per environment (e.g. `sbx2.tfstate`), so that environments have strong blast-radius isolation.
17. As a developer, I want a committed one-time bootstrap script (pwsh/az) that creates `rg-tfstate`, the Storage Account (TLS1.2 min, blob versioning, soft-delete), and the state container, so that the chicken-and-egg of `terraform init` is resolved explicitly and reproducibly.
18. As a developer, I want environments parameterized by per-env `.tfvars` files (`environments/sbx2.tfvars`, with dev/staging/prod possible later) rather than workspaces, so that the model mirrors the existing `.bicepparam`-per-env convention and avoids cross-env footguns.
19. As a developer, I want the Terraform code organized as child modules per concern (network, aks, registry, sql, redis, servicebus, keyvault), so that the structure mirrors Bicep's module-per-concern layout and each module has a clean, reusable interface.
20. As a developer, I want the Terraform version and the azurerm provider version pinned and the `.terraform.lock.hcl` committed, so that plans are reproducible across machines and CI.
21. As a developer, I want common tags applied via the provider `default_tags` (`env=sbx2`, `managedBy=terraform`), so that Terraform-owned resources are immediately distinguishable in the portal.
22. As a developer, I want the Terraform plan/apply lane to run in Azure Pipelines (a new `terraform-pipeline.yml`), so that it reuses the same CD system as the existing app deployments.
23. As a developer, I want the pipeline to authenticate via a new dedicated Workload Identity Federation service connection, so that there is no stored client secret and the existing app-CD service principals are untouched.
24. As a developer, I want that service connection scoped to the `sbx2` subscription with Contributor **and** User Access Administrator, so that the `AcrPull` role assignment can actually be created.

## Implementation Decisions

### Module 1: Terraform root + per-env configuration
- Single Terraform root with `environments/sbx2.tfvars` selected at plan/apply time via `-var-file`; additional envs added as sibling tfvars later. No workspaces.
- `azurerm` backend, one state key per env (`-backend-config` per env). Backend Storage Account created out-of-band by the bootstrap script.
- `required_version` and azurerm provider pinned (`~> 4.x`); `.terraform.lock.hcl` committed. Provider `default_tags` carry `env`/`managedBy`.

### Module 2: `network` child module
- VNet `10.50.0.0/16` with three subnets (AKS `/20`, private-endpoints `/24`, agents `/24`). Outputs subnet IDs consumed by `aks`.

### Module 3: `registry` child module
- ACR owned by `sbx2`, plus an `azurerm_role_assignment` granting `AcrPull` to the AKS kubelet identity scoped to the ACR. No deterministic GUID needed — the Terraform resource address is stable. Open item: decide whether `sbx2` manifests keep the redundant `acr-pull-secret` imagePullSecret or rely solely on the kubelet identity.

### Module 4: `aks` child module
- AKS with system-assigned managed identity, Container Insights addon wired to a Log Analytics workspace (provisioned here or via an observability sub-module). Cost-minimizing node profile (single burstable node) mirroring the existing sandbox.

### Module 5: `sql` child module
- One Azure SQL logical server; 7 databases declared via a `for_each` map keyed by service name. SQL Serverless tier with auto-pause to match the sandbox cost profile. Admin password from `random_password` (sensitive, in state only). Connection strings emitted as sensitive outputs.

### Module 6: `redis` child module
- Redis Basic C0. Primary key emitted as a sensitive output.

### Module 7: `servicebus` child module
- Service Bus namespace with 11 topics declared via a `for_each` map matching the integration-event set. Connection string emitted as a sensitive output.

### Module 8: `keyvault` child module
- RBAC-enabled Key Vault, provisioned but not wired to pods (parity with today). Key Vault CSI wiring is explicitly deferred.

### Module 9: Bootstrap script
- Committed pwsh/az script, run once by an admin: creates `rg-tfstate` + Storage Account (TLS1.2 min, blob versioning, soft-delete) + `tfstate` container. Documents the target subscription/region (recommend same subscription, southeastasia).

### Module 10: `terraform-pipeline.yml` (Azure Pipelines — CD lane)
- Authenticates via a new dedicated WIF service connection scoped to the `sbx2` subscription with Contributor + User Access Administrator.
- Stages: `Validate` (fmt/validate) → `Plan` (`terraform plan -out=tfplan`, publish artifact) → `Apply` (`terraform apply tfplan`, gated by `tf-sbx2` DevOps Environment approval). Applies the exact reviewed plan.

### Module 11: `terraform-ci.yml` (GitHub Actions — CI gate)
- Triggered on PRs touching `terraform/`. Runs `terraform fmt -check`, `terraform validate -backend=false`, `tflint`. No Azure credentials. Mirrors `docker-build.yml`'s kubeconform manifest validation.

### Module 12: `deploy-stage.yml` extension + app deploy wiring
- Extend the shared deploy template with a `sbx2` environment; add a `SBX2_` variable group and a `tf-sbx2` DevOps Environment. Each service's pipeline gains a `sbx2` stage reusing the existing `createSecret` + image-substitution flow.
- `sbx2` config sets `Qa__Seed=true` and pins `replicas=1`. Terraform sensitive outputs are surfaced into `SBX2_*` variables (the exact variable names mirror the existing `DEV_*` set — to be inventoried from ADO).

### Module 13: ADR 0015 + PRD cross-ref
- New `docs/adr/0015-terraform-as-azure-iac-option.md`: Accepted; records ownership boundary (Bicep owns dev/staging/prod/sandbox; Terraform owns `sbx2`), the greenfield-parallel constraint, ADO+WIF runner/auth, the azurerm state backend, and that it does **not** supersede Bicep. One-line cross-reference added to `docs/prd/azure-infrastructure-deployment.md`.

## Testing Decisions

- **What makes a good test here:** IaC has no business logic to unit-test; a good test validates external, observable behavior — that the configuration is syntactically valid, internally consistent, formatted to convention, and that a plan produces the intended resource set — rather than asserting on HCL internals.
- **Static gate (the primary test layer):** `terraform fmt -check`, `terraform validate -backend=false`, and `tflint` run as the GitHub Actions PR gate on every change under `terraform/`. This is the analogue of the existing kubeconform manifest gate.
- **Plan as a review test:** the Azure Pipeline's published `tfplan` artifact is the behavioral check before any mutation — the reviewer confirms the plan creates exactly the `sbx2` resource set.
- **End-to-end behavioral verification:** an `apply` against `sbx2` followed by a Bruno smoke run against the `sbx2` gateway confirms the provisioned environment actually runs the saga flow — reusing the prior art in `smoke-test.yml` (docker-compose + Bruno) and the existing per-service health checks.
- **Modules covered by the static gate:** all child modules (network, aks, registry, sql, redis, servicebus, keyvault) plus the root.
- **Prior art:** `docker-build.yml` (kubeconform validation as a PR gate), `smoke-test.yml` (Bruno end-to-end smoke), per-service `/health` checks.
- **Out of scope for testing:** a HCL unit-test framework (e.g. Terratest) and policy-as-code scanning (e.g. checkov/tfsec) — candidates for a later hardening iteration, not this one.

## Out of Scope

- Importing existing Bicep-created resources into Terraform (greenfield only).
- Replacing Bicep for dev/staging/prod or the existing `sandbox` env — Bicep remains the owner of those.
- Wiring Key Vault to pods via the CSI driver / workload identity (KV stays provisioned-but-unwired, as today).
- Multi-replica / HA topology on `sbx2` (single replica by design).
- Running the Terraform lane in GitHub Actions for `apply`, or making it runnable from both runners (Azure Pipelines only).
- OIDC/WIF migration for the existing app-CD pipelines (only the new Terraform service connection uses WIF).
- Terraform Cloud / HCP as a state or run backend.
- Terratest/checkov policy testing.

## Further Notes

- **Open items to resolve before completion (do not block starting):** (1) the exact `SBX2_*` variable names the `createSecret` task expects, to be inventoried from Azure DevOps; (2) the target subscription/region for the bootstrap `rg-tfstate`; (3) the AAD app-registration + federated-credential subject mapping for the WIF service connection (requires an AAD admin); (4) whether `sbx2` manifests keep the redundant `acr-pull-secret` or rely solely on the kubelet `AcrPull` identity.
- **Naming is normalized to `sbx2` throughout** — variable group `SBX2_*`, DevOps Environment `tf-sbx2`, state key `sbx2.tfstate`.
- **Migrations in non-sandbox envs** apply through an undocumented path (startup migration is gated off when `Qa:Seed` is unset); `sbx2` deliberately sidesteps this by enabling `Qa__Seed=true`. If `sbx2` is ever promoted toward production-shaped behavior, that path must be discovered and addressed.
- **Secrets in state:** SQL admin password and `listKeys`-equivalent outputs land in Terraform state; the `azurerm` backend (encrypted at rest, access-controlled, soft-delete) is the mitigation. Acceptable for a sandbox.
